# Forge anti-slop audit

Date: 2026-10-07. Audited revision: `a7f319f`.
Mode: after, from the user's earlier explicit session choice.

## Result

15 findings: 9 HIGH and 6 LOW, grouped below by category. The most consequential
finding is a reproduced measurement-save failure that looks successful and loses
the edit on reload. Contrast, accessible selection state, gesture-only reordering,
small targets, and narrow-screen clipping also need attention.

Forge retains a recognizable visual identity. This audit does not justify a
general redesign, replacing its icon library, removing its dock, or adding
decorative motion. No app fixes were made during this audit.

Priority follows the installed skill's tiers: Hard Gate = HIGH, Purpose-Gate =
MEDIUM, Quality Lock = LOW. These are filter priorities, not equal impact scores:
the punctuation finding is HIGH under R-02 but is much less urgent than a lost
measurement. Each finding separates runtime evidence from code inspection.

## Scope and direction

Used the core `antislop` skill and all five installed companion skills:
`antislop-ui`, `antislop-human`, `antislop-layoutmobile`,
`antislop-copywriting`, and `antislop-code`.

Forge's existing `.agents/rules/design.md` supplies the direction: a mobile workout
logger with neutral controls, Manrope, grouped tonal cards, a persistent frosted
dock, small semantic/data colors, and quiet motion tied to interaction.
Audit reading: ENERGY 1 / RHYTHM 2 / MOTION 2. These describe the existing direction
for this review; they are not a new product requirement or design policy.

Browser review covered iPhone Air/WebKit and Galaxy S24/Chromium in Light and Dark:
Dashboard, Plans, routine creation, History, workout detail, Settings, General,
duration picker, Measurements, workout types, live tracking, timed columns,
tracking confirmation, complete/incomplete finish sheets, expanded new-routine
forms, and male/female muscle maps. Tested malformed-storage and storage-full
fixtures in isolated browser contexts. Application string scanning covered 190
TS/TSX files under `src`; comment searches covered app and local native/plugin
sources. Dependency/vendor code and installed skill prose are outside app scope.

## Accessibility and controls

### 1. HIGH: enabled text has insufficient contrast

Rules: R-25, R-34; human skill, low-contrast text. Reason: several small labels use
colors intended for subdued chrome or status icons without a readable text variant.

| Actual pairing | Ratio | Evidence |
| --- | ---: | --- |
| Light muted `#8A969E` on card `#F4F5F2` | 2.77:1 | Muscle-map Low/High labels and dashboard metadata, 12px |
| Light muted `#8A969E` on white | 3.03:1 | General's enabled Search settings placeholder, 15px |
| Light destructive `#D64848` on `#F6DCDD` | 3.32:1 | Revealed History Delete label, 12px |
| Light destructive `#D64848` on card `#F4F5F2` | 3.93:1 | Inline/error text using the same token; code-level pairing |
| Light success `#4D7B67` on `#E3EEE8` | 4.07:1 | Enabled Save measurement label, 15px |
| Dark success `#6F9E87` on `#293B32` | 3.92:1 | Enabled Save measurement label, 15px |

The skill's Python contrast checker computed these ratios. Runtime measurements
confirmed the save button's text/fill/size in all four profile/theme combinations;
Delete, search placeholders, and the map legend were also visually inspected.
Sources: `src/theme/tokens.ts:58`, `src/components/ui/Button.tsx:144`,
`src/components/ui/ForgeSearchField.tsx:43`,
`src/screens/MuscleHeatmapDetailScreen.tsx:233`, and
`src/screens/dashboard/DashboardWidgetTiles.tsx:703`.

Suggested correction: use readable text variants of the muted/destructive/success
tokens while preserving Forge's semantic colors and tonal surfaces. Recheck enabled,
pressed, error, and placeholder states. Disabled actions are not counted here.

For accuracy, the skill's shorthand of 18px for large text is too permissive.
The [W3C explanation](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
uses 18pt regular or 14pt bold, approximately 24px or 18.7px bold. All failing text
listed here is below those sizes and needs 4.5:1. Borderless card tone is not
automatically a contrast defect: [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
applies to visual information needed to identify controls and states, not every
decorative surface boundary.

Artifacts: `/tmp/forge-antislop-evidence/s24-light-delete-reveal.png`,
`iphone-air-light-keyboard-search-focus.png`,
`contact-samsung-galaxy-s24-heatmap.png`, and each `*-measurement-save-ready.png`.

### 2. HIGH: Appearance radios do not expose the selected choice on web

Rules: R-26, R-32; human skill, perceivable states. Reason: the visible selection
ring changes but the browser accessibility state does not.

`src/components/ui/ForgeSegmentedSwitch.tsx:62` passes native
`accessibilityState.checked` without the browser `aria-checked` used by Forge's
other selection controls. Before and after selecting Dark, the radio's
`aria-checked` remained absent in both browsers. The app did switch to Dark, so
this is a semantics defect rather than a dead theme control.

Suggested correction: expose the actual checked state to web accessibility APIs
and verify keyboard/screen-reader announcements. Native VoiceOver/TalkBack was
not tested, so this finding does not claim their native state is missing.
Evidence: each `*-edgecases.json`, cases `appearance-selected-state` and
`appearance-switch-dark`.

### 3. HIGH: routine reordering has no keyboard equivalent

Rules: R-26, R-32; human skill, mouse-only patterns. Reason: an accessible-looking
Reorder button can only perform its action through a held pan gesture.

`src/screens/PlansScreen.tsx:929` renders a gesture-wrapped View with button role
and Reorder label. It has no Tab stop, activation handler, accessible move actions,
or alternate Move up/Move down controls. On both phone browser profiles, focusing
the handle and pressing Enter/ArrowDown kept the stored order `[r1, r2]` unchanged.
The gesture works in the existing drag tests; its keyboard equivalent is absent.

Suggested correction: offer discrete accessible move actions using the same reorder
operation, preserving the drag interaction. Review equivalent dashboard/exercise
handles before applying a shared solution; those were inspected but not separately
keyboard-reproduced here.
Evidence: `*-edgecases.json`, `reorder-keyboard` and `reorder-after-keys`;
`*-reorder-keyboard.png`.

### 4. HIGH: several primary touch targets are smaller than Forge's minimum

Rule: R-03; layoutmobile skill, under-sized targets. Reason: compact visual sizes
are also the full hit area in these controls.

Appearance segments are 34x34 with no hitSlop
(`src/components/ui/ForgeSegmentedSwitch.tsx:99`). Measurements' inline Add control
is about 59x30 with no hitSlop (`DailyMeasurementsScreen.tsx:845`), and chart range
tabs have 30px minimum height (`:796`). The first two sizes were measured in both
themes on both profiles; chart-tab sizing was inspected in source/screenshots.

Suggested correction: retain compact visual content but provide at least 44x44
effective targets with adequate separation. Do not flag the 32px information
buttons as equivalent: they already have 8px hitSlop. The 44px goal here comes
from Forge and R-03, not a claim that WCAG AA universally requires 44px.

## Mobile layout

### 5. HIGH: the Measurements header title runs underneath its actions

Rules: R-03, R-34; layoutmobile skill, clipping/collisions. Reason: the absolute
centered title does not reserve room for the wider right-hand control group.

On S24, Measurements visibly ends under the Edit/Add pill, and under Done in edit
mode, in both themes. iPhone Air fits at ordinary text size.
`src/screens/settings/SettingsScreenChrome.tsx:58` gives its title the whole header
width while the right action occupies a 100px slot. A one-line Text does not prevent
the overlap because its wrapper itself spans beneath the actions.

Suggested correction: bound the title between both action slots and reflow or
adjust its type within Forge's existing header hierarchy. Include the accepted
native text-scaling range when verifying the shared header.
Evidence: `/tmp/forge-antislop-evidence/s24-light-measurements.png` and
`s24-dark-measurements-edit.png`.

### 6. HIGH: the Measurements chart clips the 90d range control

Rules: R-03, R-34; layoutmobile skill, fixed-width children. Reason: the chart's
small half-width card cannot hold its title and all three fixed-size range choices.

The 90d choice is cut off by the card edge on S24 in Light and Dark.
`src/screens/settings/DailyMeasurementsScreen.tsx:475` places TREND and all range
tabs in one row; the base ForgeCard clips overflowing content. This is internal
clipping even though the document has no horizontal scroll.

Suggested correction: wrap or stack the range controls, or let the chart take a
full row when this content stops fitting. Do not reduce the targets further.
Evidence: `s24-light-measurements.png`, `s24-dark-measurements.png`.

## Visual consistency and hierarchy

### 7. LOW: some frosted sheet controls look square in Chromium

Rules: R-11, R-20; UI skill, consistent component treatment. Reason: the visible
frost/tint does not consistently retain Forge's circular-control silhouette.

S24 captures show a square patch around Close in tracking/finish sheets, and around
Back in the expanded new-routine state. iPhone/WebKit captures retain the circle.
The intended geometry exists in `src/components/ui/HeaderAction.tsx:112`; therefore
the screenshots establish a browser rendering defect, not a missing radius token.
Its blur/clipping root cause and native Android behavior were not established.

Suggested correction: inspect the web blur/tint layer containment and test a
targeted clipping fix. Preserve native frost and shared 44px geometry.
Evidence: `contact-samsung-galaxy-s24-tracking.png` and
`contact-samsung-galaxy-s24-finish.png`, compared with the iPhone equivalents.

### 8. LOW: ordinary duration-picker titles are truncated on the narrow profile

Rules: R-20, R-31; UI skill, hierarchy. Reason: the default header title allocation
uses symmetric margins even when only one side has a control.

Default rest time appears as Default res... on S24; it fits on iPhone Air.
`src/components/ui/ForgeSheetHeader.tsx:100` reserves 74px on each side, and
`ForgeDurationWheel.tsx` uses the ordinary title treatment. This truncation is
intentional in code, so it is a readability opportunity rather than overflow.

Suggested correction: use the existing compact/auto-shrink treatment or a shorter
contextual title for this known label. Keep full accessible names and action clearance.
Evidence: `s24-light-duration-picker.png` and `s24-dark-duration-picker.png`.

### 9. LOW: the chart eyebrow drifts from Forge's case and label hierarchy

Rules: R-06, R-20; UI skill, typography. Reason: a descriptive heading uses a
tracked all-caps caption despite Forge's sentence-case, minimum-label convention.

`src/screens/settings/DailyMeasurementsScreen.tsx:477` renders TREND using the
12px caption role with letter spacing 0.8 (`:793`). Forge reserves all caps for
compact date/calendar or abbreviation semantics and captions for non-essential
metadata. The title names the chart rather than such metadata.

Suggested correction: use Trend with the label role, then verify the range controls
still fit. This is a local consistency fix, not evidence that all captions or all
uppercase strings are wrong. Dates, RPE, kg/km, and calendar rails remain purposeful.

## Failure and recovery states

### 10. HIGH: corrupted saved data is presented as a normal empty collection

Rule: R-27; UI/human skills, missing error states. Reason: recovery failures are
indistinguishable from first use.

Isolated malformed JSON for Plans and completed workouts produced Build your first
routine and No completed workouts, without a visible error or recovery action, in
all four combinations. The malformed Plans value remained stored.
`src/data/plansRepository.web.ts:25` returns EMPTY after a read/parse error;
`src/data/workoutRepository.web.ts:9` similarly replaces parse errors with defaults.
Native provider catch paths also expose no error status, but native storage faults
were not exercised here.

Suggested correction: distinguish an absent collection from a failed load, preserve
the saved bytes, and provide an explicit retry/restore route. Avoid asking users to
populate a collection that failed to load.
Evidence: `*-corrupt-plans.png`, `*-corrupt-history.png`, and `*-edgecases.json`.

### 11. HIGH: failed measurement saves look successful and lose the edit

Rules: R-26, R-27; human skill, missing error feedback. Reason: the editor dismisses
before persistence succeeds and has no path to report the write failure.

Reproduced on both browsers in both themes with an isolated storage-full fixture:
edit 80 kg to 81 kg, then Save measurement. The sheet closed and the screen showed
81 kg, but storage still contained 80. A QuotaExceededError reached the console,
and there was no visible retry/error. Reload therefore restores the old value.

`src/state/SettingsContext.tsx:34` updates preferences optimistically and discards
the save promise. `src/screens/settings/DailyMeasurementsScreen.tsx:240` immediately
closes the record editor after that update. Plans uses a similar fire-and-forget
commit; it needs separate reproduction before claiming the same visible result.

Suggested correction: expose save completion/failure, retain the draft on failure,
show an inline retry, and prevent a dismissed editor from implying durable success.
Evidence: `*-savefailure.json` and `*-measurement-save-failed.png`.

## Copy and content

### 12. HIGH under the skill: explanatory sentences still use em dashes

Rule: R-02; copywriting skill. Reason: several interface sentences retain the
punctuation expressly rejected by this filter.

Confirmed in the Dashboard empty state at `src/screens/DashboardScreen.tsx:450`,
the measurement widget empty state (`DashboardWidgetTiles.tsx:431`), goal-setting
help (`DashboardTileSettingsSheet.tsx:319`), import notices
(`SettingsDestinationScreen.tsx:371`, `:527`), and the active-workout guard
(`useStartWorkoutGuard.tsx:37`). The Dashboard sentence was visually inspected;
the other sentences are code-level findings.

Suggested correction: use a colon or separate sentences while retaining the exact
meaning. Example: Add the widgets you want to see: stats, streaks, measurements and
more. Do not blindly replace missing-value glyphs or range parsing expressions;
those serve data/input semantics and are not prose flourishes.
This is a minor editorial change despite the skill's HIGH label, and no evidence
of who authored the text.

### 13. LOW: History does not pluralize its exercise/set summary

Rules: R-15, R-20; copywriting skill, specific readable product text. Reason: the
one-item state reads 1 exercises, 1 sets rather than matching its data.

`src/screens/HistoryScreen.tsx:666` always uses plural nouns. The one-exercise,
one-set fixture reproduced it in all four combinations. WorkoutSummaryCard
already handles the same singular/plural distinction correctly.

Suggested correction: share or mirror the correct singular/plural formatting.
On narrow History cards, preserve the deciding information before optional
metadata so the summary does not disappear behind the duration chip.
Evidence: each `*-history.png`, compared with `*-workout-detail.png`.

## Code comments

### 14. LOW: decorative section banners add noise to metric logic

Rule: R-31; code skill, decorative separators. Reason: repeated long dashed lines
surround labels that can stand on their own.

`src/domain/dashboard/widgetMetrics.ts:16`, `:187`, `:244`, `:306`, `:379`, and `:434`
use repeated separator banners. Some headings carry useful group descriptions;
the repeated-character decoration does not.

Suggested correction: remove just the banner lines, retaining concise descriptions
of muscle grouping and metric contracts. Do not change executable code.

### 15. LOW: useful comments are overlong, and one card explanation is stale

Rule: R-31; code skill, over-explained comments. Reason: platform/design explanations
repeat facts already held by canonical rules, and one contradicts current tokens.

`src/theme/scale.ts:3` spends a long opening block and several repeated paragraphs
explaining the reference canvas/downscale policy. `ForgeWheelColumn.tsx:28` also
recounts a past rendering bug at length. Preserve their constraints, but shorten
the history and duplicated design rationale. These are useful comments, not
instructions to erase the workarounds.

`src/components/ui/ForgeCard.tsx:41` says Light surface and surfaceElevated are equal.
They are currently `#F4F5F2` and `#FFFFFF`. The comment now gives the wrong rationale
for separation. Suggested correction: state the current tone/shadow constraint in
one or two lines and leave the card implementation alone.
