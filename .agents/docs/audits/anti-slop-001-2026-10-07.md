## Accessibility and controls

### 1. HIGH: enabled text has insufficient contrast

Rules: R-25, R-34; human skill, low-contrast text. Reason: several small labels use
colors intended for subdued chrome or status icons without a readable text variant.

| Actual pairing | Ratio | Evidence |
| --- | ---: | --- |
| Light muted `#8A969E` on card `#F4F5F2` | 2.77:1 | Muscle-map Low/High labels and dashboard metadata, 12px |
| Light muted `#8A969E` on white | 3.03:1 | General's enabled Search settings placeholder, 15px |
| Light destructive `#D64848` on `#F6DCDD` | 3.32:1 | Revealed History Delete label, 12px |
| Light destructive `#D64848` on card `#F4F5F2` | 3.93:1 | Inline/error text using the same token; code-level pairing |
| Light success `#4D7B67` on `#E3EEE8` | 4.07:1 | Enabled Save measurement label, 15px |
| Dark success `#6F9E87` on `#293B32` | 3.92:1 | Enabled Save measurement label, 15px |

The skill's Python contrast checker computed these ratios. Runtime measurements
confirmed the save button's text/fill/size in all four profile/theme combinations;
Delete, search placeholders, and the map legend were also visually inspected.
Sources: `src/theme/tokens.ts:58`, `src/components/ui/Button.tsx:144`,
`src/components/ui/ForgeSearchField.tsx:43`,
`src/screens/MuscleHeatmapDetailScreen.tsx:233`, and
`src/screens/dashboard/DashboardWidgetTiles.tsx:703`.

Suggested correction: use readable text variants of the muted/destructive/success
tokens while preserving Forge's semantic colors and tonal surfaces. Recheck enabled,
pressed, error, and placeholder states. Disabled actions are not counted here.

For accuracy, the skill's shorthand of 18px for large text is too permissive.
The [W3C explanation](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
uses 18pt regular or 14pt bold, approximately 24px or 18.7px bold. All failing text
listed here is below those sizes and needs 4.5:1. Borderless card tone is not
automatically a contrast defect: [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
applies to visual information needed to identify controls and states, not every
decorative surface boundary.

Artifacts: `/tmp/forge-antislop-evidence/s24-light-delete-reveal.png`,
`iphone-air-light-keyboard-search-focus.png`,
`contact-samsung-galaxy-s24-heatmap.png`, and each `*-measurement-save-ready.png`.

### 2. HIGH: some selection controls omit their selected state on web

Rules: R-26, R-32; human skill, perceivable states. Reason: the visible selection
ring changes but the browser accessibility state does not.

`src/components/ui/ForgeSegmentedSwitch.tsx:62` passes native
`accessibilityState.checked` without the browser `aria-checked` used by Forge's
other selection controls. Before and after selecting Dark, the radio's
`aria-checked` remained absent in both browsers. The app did switch to Dark, so
this is a semantics defect rather than a dead theme control. The refreshed browser check
also found absent `aria-selected` on Exercise Library's leading-side buttons,
although selecting Right persisted the preference. `ExerciseDetailBody.tsx` uses
native `accessibilityState.selected` without the explicit web attribute. This is
the same native/web semantics gap, rather than a separate visual defect.

Suggested correction: expose the actual checked state to web accessibility APIs
and verify keyboard/screen-reader announcements. Native VoiceOver/TalkBack was
not tested, so this finding does not claim their native state is missing.
Evidence: each `*-edgecases.json`, cases `appearance-selected-state` and
`appearance-switch-dark`.

### 3. HIGH: routine reordering has no keyboard equivalent

Rules: R-26, R-32; human skill, mouse-only patterns. Reason: an accessible-looking
Reorder button can only perform its action through a held pan gesture.

`src/screens/PlansScreen.tsx:935` renders a gesture-wrapped View with button role
and Reorder label. It has no Tab stop, activation handler, accessible move actions,
or alternate Move up/Move down controls. On both phone browser profiles, focusing
the handle and pressing Enter/ArrowDown kept the stored order `[r1, r2]` unchanged.
The gesture works in the existing drag tests; its keyboard equivalent is absent.

Suggested correction: offer discrete accessible move actions using the same reorder
operation, preserving the drag interaction. Review equivalent dashboard/exercise
handles before applying a shared solution; those were inspected but not separately
keyboard-reproduced here.
Evidence: `*-edgecases.json`, `reorder-keyboard` and `reorder-after-keys`;
`*-reorder-keyboard.png`.

### 4. HIGH: several primary touch targets are smaller than Forge's minimum

Rule: R-03; layoutmobile skill, under-sized targets. Reason: compact visual sizes
are also the full hit area in these controls.

Appearance segments are 34x34 with no hitSlop
(`src/components/ui/ForgeSegmentedSwitch.tsx:99`). Measurements' inline Add control
is about 59x30 with no hitSlop (`DailyMeasurementsScreen.tsx:845`), and chart range
tabs have 30px minimum height (`:796`). The first two sizes were measured in both
themes on both profiles; chart-tab sizing was inspected in source/screenshots.

Suggested correction: retain compact visual content but provide at least 44x44
effective targets with adequate separation. Do not flag the 32px information
buttons as equivalent: they already have 8px hitSlop. The 44px goal here comes
from Forge and R-03, not a claim that WCAG AA universally requires 44px.

## Failure and recovery states

### 10. HIGH: corrupted saved data is presented as a normal empty collection

Rule: R-27; UI/human skills, missing error states. Reason: recovery failures are
indistinguishable from first use.

Isolated malformed JSON for Plans and completed workouts produced Build your first
routine and No completed workouts, without a visible error or recovery action, in
all four combinations. The malformed Plans value remained stored. In the fresh
probe, malformed completed-History bytes were replaced with `[]` during load in
all four combinations. This is data replacement as well as misleading empty-state
presentation; recovery cannot rely on those original bytes remaining available.
`src/data/plansRepository.web.ts:25` returns EMPTY after a read/parse error;
`src/data/workoutRepository.web.ts:9` substitutes parse-error defaults and its
load-time canonicalization writes the resulting empty collection back at line 42.
Native provider catch paths also expose no error status, but native storage faults
were not exercised here.

Suggested correction: distinguish an absent collection from a failed load, preserve
the saved bytes, and provide an explicit retry/restore route. Avoid asking users to
populate a collection that failed to load.
Evidence: `/tmp/forge-antislop-54bff3b/*-corrupt-plans.png`,
`*-corrupt-history.png`, and `*-edgecases.json` (including raw stored values).

### 11. HIGH: failed measurement saves look successful and lose the edit

Rules: R-26, R-27; human skill, missing error feedback. Reason: the editor dismisses
before persistence succeeds and has no path to report the write failure.

Reproduced on both browsers in both themes with an isolated storage-full fixture:
edit 80 kg to 81 kg, then Save measurement. The sheet closed and the screen showed
81 kg, but storage still contained 80. A QuotaExceededError reached the console,
and there was no visible retry/error. Reload therefore restores the old value.

`src/state/SettingsContext.tsx:35` updates preferences optimistically and discards
the save promise. `src/screens/settings/DailyMeasurementsScreen.tsx:240` immediately
closes the record editor after that update. Plans uses a similar fire-and-forget
commit; it needs separate reproduction before claiming the same visible result.

Suggested correction: expose save completion/failure, retain the draft on failure,
show an inline retry, and prevent a dismissed editor from implying durable success.
Evidence: `*-savefailure.json` and `*-measurement-save-failed.png`.

## Press feedback

### 16. LOW, addressed: pressed layers did not follow the full visible surface

Rules: R-11, R-20, R-26; UI/human skills, consistent and perceivable control states.

The user reported routine-name tint omitting the leading icon/padding, square
Calendar feedback, and a square leading-side highlight over rounded segments.
The broader source scan also found larger rectangular wrappers around Dashboard
day dots, live and History set-number chips, and bilateral/unilateral completion
circles. Those invisible touch extensions are not the visible control silhouette.
History editor selector wrappers also included static labels above the value buttons.

The shared primitive now supports an inset shaped layer and a shared visual group.
Routine actions highlight the full row while Start remains a separate accessible
action. Calendar and Dashboard highlight circles; chips and completion controls
retain their visible radii and larger hit targets; both leading-side options use
the pill radius. History selector labels stay outside the buttons; only the rounded
value buttons receive tint. Ordinary grouped
rows still tint their full row and inherit the enclosing card's corner clipping.
Disabled controls and dismissal backdrops do not gain a feedback layer.

Browser tests verified geometry, state-layer removal, independent routine actions,
leading-side persistence, completion updates and disabled Calendar behavior.
Inspected captures cover the exact reported states in both themes on both phone
profiles. These checks do not establish native keyboard or gesture cancellation
behavior on physical devices.

Guidance consulted:
[Apple custom-button states](https://developer.apple.com/design/human-interface-guidelines/buttons),
[Material state-layer surfaces](https://github.com/material-components/material-web/blob/main/docs/components/ripple.md),
[React Native Pressable](https://reactnative.dev/docs/Pressable), and
[React Native radius/clipping properties](https://reactnative.dev/docs/view-style-props).
Apple calls for a pressed state on custom buttons; Material describes a translucent
state layer with the component's relevant surface shape. Forge applies those
principles through its existing tint tokens, without adding ripples or scale motion.
Clickable buttons, rows, tabs, swatches and segmented options need feedback.
Decorative icons, labels, charts, noninteractive cards, disabled actions and gesture-only
surfaces do not need an additional button tint. Text inputs retain input focus feedback;
wheels, sliders and native switches retain their own interaction states.

Evidence: `/tmp/forge-antislop-54bff3b/pressed/`;
`press-feedback-shapes.spec.ts`, `routine-press-feedback.spec.ts`,
`app-press-feedback.spec.ts`.
