## Findings

### 1. HIGH: Imported measurements can disappear from the normal workout presentation

**Status: presentation recommendation superseded by explicit user direction; data preservation remains required. Rules: R-26, C-4.** The user requested removal of the added History summary and imported-measurements section in set details on 2026-10-09. Both components were restored to their WIP checkpoint presentation. Extra source measurements remain preserved through resolution and portable backup; values outside the tracking fields are not shown in those existing views. The visibility recommendation below is historical advisory evidence, not an outstanding authorization to change those screens.

Locations: `src/data/csvImport/parse.ts:187`, `src/data/csvImport/review.ts:61`, `src/domain/exercises/tracking.ts:16`.

Reproduction: parse a Hevy row containing `weight_kg=50`, `reps=8`, and `duration_seconds=30`; resolve the exercise as custom. The importer infers `duration-weight`. The stored set retains all three measurements, but `measurementsFor(effectiveTracking(block), set)` returns only 50 kg and 30 sec. The eight reps are filtered out. This is a visibility/measurement-mode defect, not evidence that the stored source value was erased. The compatibility fallback also uses the inferred source mode, which cannot represent every combination.

Recommended correction: preserve access to all supported source measurements in the imported workout presentation, including combinations beyond one tracking mode's fields. Cover mixed-metric sets and mappings to loaded bodyweight modes without guessing exercise anatomy/equipment.

Evidence: `/tmp/forge-import-audit/probe.cjs` and `probe-results.txt`; the existing preservation test covers simpler combinations and passes despite this case.

### 2. HIGH: The documented FitNotes iOS CSV header is rejected

**Status: fixed; see authorized follow-up. Rule: R-26.** Reason: a file exported in a supported app's documented format should reach review. The reproduction below records the original audit state.

Locations: `src/data/csvImport/adapters.ts:44`, `src/data/csvImport/adapters.ts:124`, `tests/unit/csv-import.spec.ts:209`.

The [official FitNotes iOS format](https://www.getfitnotes.com/docs/migrate-from-other-apps.html) uses `Weight (kg)` and `Weight (lbs)`. Header normalization trims and lowercases, but preserves the internal space. Detection and extraction accept only `weight(kg)` and `weight(lbs)`. A fixture with the complete documented header throws `CSV is missing required columns: weight.` The current iOS fixtures use the unspaced spelling, so green tests do not establish compatibility with the documented export.

Recommended correction: accept the documented spellings in both detection and extraction, retain supported legacy spellings, and use a fixture matching the official header. Keep malformed-header rejection.

Evidence: official format above and `/tmp/forge-import-audit/probe-results.txt`, first line.

### 3. HIGH: Valid FitNotes iOS distance units exclude the workout

**Status: fixed; see authorized follow-up. Rule: R-26.** Reason: supported source measurements should normalize to Forge units rather than invalidate otherwise valid sessions. The reproduction below records the original audit state.

Location: `src/data/csvImport/parse.ts:351`.

The same official format supports `cm`, `in`, `ft`, and `yd` alongside `m`, `km`, and `mi`. The parser accepts only the latter group and mile aliases. A recognized-header iOS row with `Distance=100`, `Distance Unit=ft`, and `Time=60` produces a row-2 Distance problem and excludes its workout. This reproduction uses the currently accepted unspaced weight header to isolate the unit problem from finding 2.

Recommended correction: convert all documented finite distance units to canonical kilometres and add individual conversion fixtures. Continue rejecting unknown units and excluding a genuinely invalid workout as a whole.

Evidence: `/tmp/forge-import-audit/probe-results.txt`, final line. No new dependency or product decision is needed.

### 4. HIGH: Changed exercise matches cannot be remembered on duplicate-only imports

**Status: fixed; see authorized follow-up. Rules: R-26, R-27.** Reason: a match the user changes during a later import should have a reachable persistence path. The reproduction below records the original audit state.

Locations: `src/screens/settings/csvImport/CsvImportScreen.tsx:99`, `src/screens/settings/csvImport/CsvImportScreen.tsx:422`, `src/data/csvImport/review.ts:241`.

Reproduction: import a CSV, open the same CSV again, and change an exercise match. All sessions remain duplicates because their source fingerprints match. The final action is disabled because there are no actionable workouts. Independently calling `prepareCsvCommit` with the changed resolution returns zero writes and an empty mappings object: mappings are filtered to exercises used by workout writes. The new confirmed mapping is therefore discarded. Existing workout records should remain duplicates; this finding does not recommend rewriting them.

Recommended correction: provide an explicit way to confirm and persist changed valid mappings during a duplicate-only review, while preserving duplicate workout suppression, cancellation semantics and atomic persistence for any required custom target.

Evidence: `/tmp/forge-import-audit/probe-results.txt`, `statuses:["duplicate"], writes:0, mappings:{}`. Current repeat-import tests verify remembering a match saved with a new workout, not changing it in a duplicate-only review.
